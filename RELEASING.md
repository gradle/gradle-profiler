# Releasing Gradle Profiler

Do these steps in order:

1. **Prepare the release notes.** The release draft has the final notes.
2. **Set the release version** on `master`.
3. **Publish the release.** The artifacts are on Maven Central, the tag is pushed, and the GitHub release is published.
4. **Check the release.** The tag, the GitHub release and Maven Central have the new version.
5. **Request SDKMAN publishing.** For a final version, the DevProd team has what they need to publish it.
6. **Set the next development version** on `master`.

A *final version* has only numbers and dots, e.g. `0.26.0` or `0.26.1`.
A *pre-release version* has the `-alpha-<number>` suffix, e.g. `0.27.0-alpha-1`.
For [pre-release versions](#pre-release-versions) and [patch versions](#patch-versions), some steps are different.

## Steps

### 1. Prepare the release notes

The [release draft](https://github.com/gradle/gradle-profiler/releases) is generated by release-drafter from the titles and labels of the PRs merged since the last release.
The section depends on the label: `enhancement`, `bug` or `internal` ([config](.github/release-drafter.yml)).
With `no-changelog`, the PR is not listed.
Each PR needs one of these four labels ([label check](.github/workflows/enforce-labels.yml)); a PR without one is listed above all headings.

Fix titles and labels on the PRs, not in the draft: manual edits of the draft are lost on the next refresh.
The draft is refreshed on each push to `master` ([workflow](.github/workflows/release-drafter.yml)).
To refresh it without a push, re-run the latest [Release Drafter run](https://github.com/gradle/gradle-profiler/actions/workflows/release-drafter.yml).
Then check that the draft is tagged exactly `v<version>`, and that no entries are above the headings.

These [GitHub CLI](https://cli.github.com/) commands can be helpful:

```sh
# Refresh the draft by re-running the latest Release Drafter run
gh run rerun "$(gh run list --workflow release-drafter.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
# Show the name, tag and notes of the draft
gh api repos/gradle/gradle-profiler/releases --jq '.[] | select(.draft) | "\(.name) (\(.tag_name))\n\n\(.body)"'
```

### 2. Set the release version

Merge a PR with the `no-changelog` label that sets `profiler.version` in `gradle.properties` to the release version, e.g. `0.26.0`.
Keep other changes out of this PR: with `no-changelog`, they are not listed in the notes.

Merge nothing else until step 3 is done.
The draft lists each merged PR, but the release has only the commits up to this merge.

### 3. Publish the release

Publish the version with [this TeamCity build](https://builds.gradle.org/buildConfiguration/GradleProfiler_GradleProfilerPublishing?branch=%3Cdefault%3E) on `master`.
The artifacts are uploaded to Maven Central, and the `v<version>` tag is created and pushed.
For a final version, the distribution ZIP is also attached to the draft, and the draft is published as the latest release.

The tag goes on the commit that the build checks out, so before you start it, make sure that `master` is still at the merge commit from step 2.
The build does not wait for CI.
Preferably, wait until CI passes on the merge commit.
When the version change is the only new commit, the latest completed runs on `master` are sufficient.
Some tests are flaky, e.g. [#732](https://github.com/gradle/gradle-profiler/issues/732), so a single failed job does not have to block the release.
For the exact tasks, see the [build definition](.teamcity/src/main/kotlin/GradleProfilerPublishing.kt).

> [!WARNING]
> The GitHub release is the last part of the build, and needs a draft with the tag `v<version>` exactly.
> Without one, the build fails after the upload to Maven Central and the tag push.
> This can happen for [patch versions](#patch-versions).

This [TeamCity CLI](https://jb.gg/tc/docs) command can be helpful:

```sh
# Start the publishing build pinned to the merge commit, and follow it until it finishes
teamcity run start GradleProfiler_GradleProfilerPublishing --branch master --revision <merge-commit> --watch
```

### 4. Check the release

- The tag `v<version>` points at the merge commit from step 2.
- The [GitHub release](https://github.com/gradle/gradle-profiler/releases) is published, is the latest, and has `gradle-profiler-<version>.zip` attached.
- The artifacts are on [Maven Central](https://repo1.maven.org/maven2/org/gradle/profiler/gradle-profiler/), usually 10 to 30 minutes after the build.
  The upload is published automatically; there is nothing to do in the Sonatype Central Portal.

Helpful commands:

```sh
git ls-remote --tags origin v<version>
# Expect the new version first, marked as Latest
gh release list --limit 1
# Expect isDraft false and the ZIP in the assets
gh release view v<version> --json isDraft,assets --jq '{isDraft, assets: [.assets[].name]}'
# Expect 200 when Maven Central has the version
curl -s -o /dev/null -w '%{http_code}\n' https://repo1.maven.org/maven2/org/gradle/profiler/gradle-profiler/<version>/gradle-profiler-<version>.pom
```

### 5. Request SDKMAN publishing

For a final version, ask the DevProd team to publish it to SDKMAN by hand.
For what to send them, see [SDKMAN](#sdkman).

### 6. Set the next development version

After step 3 succeeds, merge a PR with the `no-changelog` label that sets `profiler.version` to the next minor version with `-alpha-1`, e.g. `0.27.0-alpha-1`.

## Pre-release versions

Pre-release versions are normally used for dogfooding in the [gradle/gradle](https://github.com/gradle/gradle) build.
They are released from `master`, or from another branch to dogfood changes that are not on `master` yet.

A version can be published to Maven Central only once, so each alpha number can be used only once, on any branch.
Before you release one, check that its tag does not exist yet.

Versions that contain `snapshot` or `alpha` are not published to GitHub Releases or SDKMAN.

### From `master`

During development, `master` already has an `-alpha-<number>` version.

- Skip steps 1 and 2. The draft stays a draft for the next final version.
- In step 3, the tag is pushed and the artifacts are uploaded as usual, but no GitHub release is published.
- In step 4, check only the tag and Maven Central.
- Skip step 5.
- In step 6, increment the number, e.g. `0.27.0-alpha-1` → `0.27.0-alpha-2`.

### From another branch

- On the branch, set `profiler.version` to an alpha number that has no tag yet, and push the branch.
- Run the build of step 3 on that branch.
- In step 4, check only the tag and Maven Central.
- If `master` has the same alpha number, increment it in a PR with the `no-changelog` label.

## Patch versions

A patch version, e.g. `0.26.1`, has fixes on top of a released version.
Release it from a branch based on the release tag, not from `master`, because `master` can have changes that are not released yet.
No patch version has been released this way yet.

1. Create a branch from the release tag, e.g. `release-0.26.x` from `v0.26.0`.
   Add the fixes, set `profiler.version` to `0.26.1`, and push the branch.
   The fixes also go to `master` through the usual PRs.
2. Create a draft release by hand, with the name `0.26.1`, the tag `v0.26.1`, the patch branch as target, and the release notes.
   Keep the release-drafter draft for the next minor version as it is.
3. Run the build of step 3 on the patch branch.
4. Do steps 4 and 5 as for a final version.
   Skip step 6: `master` does not change.

On the next push to `master`, the patch draft can be overwritten with the notes for the next minor version ([config](.github/release-drafter.yml)).
Create the patch draft immediately before you start the build, and push nothing to `master` in between.

The published release is always marked as the latest.
If a newer minor version is already released, mark that one as the latest again, and do not ask for the patch version to become the default on SDKMAN.

## SDKMAN

Publishing to SDKMAN is manual at the moment ([#861](https://github.com/gradle/gradle-profiler/issues/861)).
The SDKMAN vendor keys are not available, so the automatic trigger of [Publish to SDKman](https://builds.gradle.org/buildConfiguration/GradleProfiler_GradleProfilerPublishToSdkMan?branch=%3Cdefault%3E) is disabled ([definition](.teamcity/src/main/kotlin/GradleProfilerPublishToSdkMan.kt)).

In [step 5](#5-request-sdkman-publishing), ask the DevProd team to publish the version to SDKMAN by hand, and give them:

- the SDKMAN candidate: `gradleprofiler`,
- the version, e.g. `0.26.0`,
- the archive: `https://github.com/gradle/gradle-profiler/releases/download/v<version>/gradle-profiler-<version>.zip`.

Also ask them to set it as the default version.

Until the version is on SDKMAN, the `sdk install` line in the release notes does not work.
